# CL 磁盘耗尽复盘与 SQLite 存储方案

日期：2026-11-07。范围：本地 CharacterLife 鲸鲸数据库。
下文明确区分已完成修复与后续设计，建议参数尚未写入运行配置。

## 1. 结论与证据

直接故障条件是 C 盘可用空间降为 0。根因是高频保存完整状态、无限追加历史快照，
同时缺少容量预算、留存策略与低空间保护。

| 检查项 | 实测结果 |
|---|---:|
| 优化前主数据库 | 93,662,269,440 字节，87.23 GiB |
| 当时 WAL | 5,108,856 字节，约 4.9 MiB |
| 快照数 | 159,919 |
| 最新连续快照 | payload 各约 676,160 字符，last_event_seq 均为 707 |
| 原库头部空闲页 | 0 |
| 精简后主数据库 | 299,425,792 字节，约 285.55 MiB |
| 精简后快照数 | 32，最新仍为 #159919 |

这说明主要空间来自重复历史快照及其存储开销。WAL 当时只有约 4.9 MiB，
并非本次 87 GiB 占用的来源；空闲页为 0，也说明直接对原库执行 VACUUM
并不能先消除仍然有效的重复记录。

可确认的写入链路如下：

1. relay 设置每 2 秒执行一次游戏轮询。
2. 世界观察被 API 接收后，`onObservations` 调用 `syncWorld()`。
3. `syncWorld()` 同步扩展状态并调用 `saveSnapshot()`。
4. 原 `snapshotInstance()` 每次保存最新状态，并向快照表追加整个状态 JSON。
5. 原 `saveSnapshot()` 没有数量、时间或字节配额，也不合并相邻保存。

每次轮询是否产生被接受的观察仍受桥接层过滤影响，不能把 2 秒直接认定为
历史上每份快照的精确间隔。但代码链路和大量相同事件序号的连续快照，共同证实
了高频完整快照的增长机制。事件序号不变也不代表 runtime 没变化，不能只按该序号去重。

## 2. 故障影响与边界

- 检查工具启动报“磁盘空间不足”；普通 SQLite 查询出现 disk I/O error。
- 检查时 CL 的 8787/8788 服务已离线，relay/语音服务仍在。
- 没有取得 CL 退出时的完整异常栈，不能断言具体哪次数据库调用导致服务退出。
- 早期绕过 WAL 读取主库的探测报 malformed，不能据此认定原库损坏。
  后续正常读取 WAL 的一致视图、数据迁移、恢复与账本核验均成功。
- 没有证据表明操作系统发生了整机崩溃；这里的“崩盘”指磁盘耗尽及相关服务不可用。

## 3. 处理过程与最终结果

1. 只读统计目录和文件，定位 87.23 GiB 主库。
2. 通过 Windows 文件压缩释放维护空间；空间够用后停止压缩，避免持续争用磁盘。
3. 新增回归测试，确认旧实现无界追加；修复后按实例最多保留 32 份，
   同一 UTC 墙钟 5 分钟区间更新最新快照，跨区间才增加一份。
4. 将修复同时应用到开发仓库及鲸鲸实际使用的 vendor 内核。
5. 在服务离线状态下，以一致只读事务构建候选库；只裁减旧快照，完整复制其他表。
6. 逐表核对行数与内容摘要，保留 schema、索引、触发器、序列高水位和版本参数；
   检查完整性及外键，切换前再次核验，再 checkpoint 原 WAL 后切换。
7. 在正式库独立副本上运行实际服务内核恢复，8 步全通过；137 条记忆可读，
   51,235 条账本哈希链完整，最新恢复点仍为 #159919、事件序号 707。
8. 用户授权后删除本次完整旧库备份，释放约 52.12 GiB；删除后 C 盘可用约
   87.17 GiB。其他系统活动也会改变可用空间。更早的小型版本迁移备份未在此轮删除。

保全的数据还包括 707 条事件、18 个会话、736 条上下文统计、4,629 条已处理消息。
内核全量回归、快照边界/回滚测试、114 项鲸鲸集成测试、类型检查及独立审查通过。
本次没有启动原先已离线的 CL 服务，也没有生成模型对话。

## 4. 当前修复的能力与局限

已实现：每实例快照数量上限、桶内合并、事务内更新与清理、失败回滚，以及
可验证的离线重建/切换工具。

仍未实现：按状态版本跳过无效保存、分区持久化、数据字节配额、容量监控、
低空间降级、账本归档与备份自动轮换。

同一时间桶内仍可更新完整 JSON；保存时间变化也可能触发写入。因此本次限制了
快照累计占用，却没有彻底消除频繁序列化、整行更新和 WAL 写放大。
32 份快照也不是固定容量：单份 payload 变大，保留总量仍会增加。

## 5. 推荐存储结构

继续使用本地 SQLite。优先把写入语义和数据生命周期做清楚，再评估是否需要换数据库。

| 数据 | 推荐保存方式 | 生命周期 |
|---|---|---|
| 角色配置、记忆、关系与关键业务状态 | 小事务持久化，保存后再确认成功 | 长期保留 |
| 最新运行状态 | 按 dirty section / stateVersion 更新，只修改变化的部分 | 每实例一份当前状态 |
| 恢复检查点 | 定期完整快照或按版本引用分块内容 | 数量与字节双重上限 |
| 世界观察、临时感知、调试上下文 | 去重、采样、设过期时间，避免整段历史嵌入快照 | 短期留存 |
| 事件与完整性账本 | 在线保留近期数据，旧 payload 可归档；保留链头和段清单 | 可校验长期归档 |
| 截图、音视频、大型外部内容 | 独立文件，数据库存路径、哈希和必要元数据 | 单独设配额 |

归档账本不能直接 DELETE 或把 `content_json` 改成 NULL：现有语义可能把 NULL 当作
删除/擦除。需新增明确的归档位置与存储状态，并让读取器能取回内容、验证 content_hash。
每段归档记录实例、起止 seq、首条 prev_hash、末条 hash、行数及归档校验和。
归档写入并验证完成、原子发布清单后，才在事务中替换在线存储引用；失败保持原内容。
若分成多个 WAL 数据库，跨库事务不具备整组原子性，需使用可重试的归档任务或 outbox，
不能把“两个库各自提交成功”当作一个原子提交。[SQLite WAL 官方说明](https://sqlite.org/wal.html)

## 6. 分阶段实施

### P0：防止再次占满磁盘

- 每 60 秒记录主库、WAL、备份和外部资产的逻辑大小、实际分配空间、磁盘剩余空间
  及增长速度，避免 NTFS 压缩造成统计误判。
- 初始建议：主库 512 MiB 提醒、1 GiB 启动归档；磁盘剩余 10 GiB 告警、
  5 GiB 停止非必要采集，2 GiB 进入受限模式。这些是本项目建议值，需按实测调整。
- 对 `SQLITE_FULL`、I/O 和空间不足错误停止无条件重试，回滚事务，停止自动扩张，
  明确报告未保存状态。低空间下也不能保证关键写入一定成功。
- 主库可选 2 GiB 软预算；如采用 `max_page_count` 最终上限，按实际 page_size 计算，
  并在所有写连接初始化时校验。它只限制该数据库页数，不限制 WAL、临时文件或备份。

### P1：减少写入量

- 引入独立 stateVersion/dirty sections；状态没变不序列化整份快照。
- 不把墙钟刷新当作业务状态变化。恢复所需时间锚点单独保存，不能简单忽略模拟时间。
- 游戏高频临时状态可先按 1–5 秒窗口合并；关键记忆、用户承诺和必须持久化的变化
  仍在事务提交后确认成功，允许丢失的短暂状态才使用延迟保存。
- 让关键状态、记忆、对应事件在同一逻辑事务中提交；检查点按已提交版本生成。
- 在现有 32 份上限外，增加每实例快照总字节预算，例如 64 MiB；单份超过 1 MiB
  告警并定位增长 section。超限时优先减少旧恢复点、迁出冗余内容，不能直接截断 JSON。
- 验收指标：无变化轮询不写完整 payload；固定状态长时间轮询后快照数、主库和 WAL
  不持续线性增长；重启后的最新业务版本、记忆及账本一致。

### P2：生命周期与归档

- 高频观察按事件 ID/语义内容去重；调试记录可采用 7–30 天起始留存期。
- 已处理消息去重表按重投窗口设置 TTL，不能随意清空后导致旧消息重复执行。
- 账本归档按日期或容量分段，先完成读取和校验支持再迁移已有内容。
- 冷归档可压缩，热库优先降低重复内容与写放大，文件系统压缩仅作为可选附加措施。

### P3：维护、备份与恢复演练

- 在线备份使用 SQLite Backup API；备份成功并校验后再轮换旧备份。
- 建议保留最近 3 份本地备份，初始总预算 5 GiB；超过预算时先告警并外迁或调整策略，
  不在新备份验证前删除唯一可用备份。[SQLite Backup API](https://sqlite.org/backup.html)
- 每日 quick_check、定期完整 integrity_check 和真实恢复演练；外键单独检查。
- 持续记录 `page_count`、`freelist_count` 与 page_size。空闲页可供后续写入复用，
  DELETE 后文件通常不会立即缩小；不需要每次删除都 VACUUM。
- 大量清理后按空闲比例和实际空间需求安排低峰压缩；保证目标文件和日志有足够空间。
  VACUUM INTO 复制的是原库现有逻辑内容，不能自动识别和移除业务冗余快照。
  [SQLite VACUUM](https://www.sqlite.org/lang_vacuum.html)

## 7. 建议连接参数（后续实现参考）

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;
PRAGMA synchronous = FULL;
PRAGMA busy_timeout = 5000;
PRAGMA wal_autocheckpoint = 1000;
PRAGMA journal_size_limit = 67108864;
```

保留 FULL 作为关键角色状态的默认持久性策略；NORMAL 需明确接受断电时最近提交
可能回滚的取舍。本次优化不以降低持久性来换取空间。`busy_timeout` 处理锁等待，
不解决磁盘满。1000 页的 checkpoint 阈值在 4 KiB 页下约 4 MiB，但不是 WAL 硬上限。
长读事务可拖延 checkpoint；`journal_size_limit` 限制重置/检查点后遗留文件大小，
也不是活动 WAL 的实时硬上限。低峰运行 PASSIVE checkpoint 并监控 busy/log/checkpointed，
有必要再在维护窗口使用 TRUNCATE。[SQLite PRAGMA](https://sqlite.org/pragma.html)

新建或重建库时可评估 `auto_vacuum=INCREMENTAL`，再配合小批量 incremental_vacuum；
已有库从 NONE 改为该模式需要重建/VACUUM，并非设一个参数就能生效。
选择它前先测量页搬移成本，不默认每次提交都做 FULL auto-vacuum。

## 8. 后续验收条件

1. 无状态变化的长时间轮询，完整快照写入次数接近 0。
2. 有状态变化时，stateVersion、dirty sections 与时间锚点一致恢复，
   检查点数量与字节均不超过策略预算。
3. 磁盘低空间和锁等待测试能进入受限模式，无无限重试或无界队列。
4. 归档前后账本链校验一致，故障注入后可恢复，归档不能破坏删除/擦除语义。
5. 备份包含 WAL 中已提交数据，备份中断不破坏原库，轮换后仍有可用恢复点。

本次已完成的验收见 `storage-optimization-20261107.md`；上述 P0–P3 属于后续方案，
尚未作为本轮新增功能实施。
