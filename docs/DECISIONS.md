# 技术取舍与未解决问题

记录「为什么这样做」「放弃了什么」「还差什么」。所有数字来自本仓库实际运行结果，
不是估计；不确定的地方会明确标注。

---

## 1. 技术选型

| 决策 | 选择 | 理由 | 代价 |
|---|---|---|---|
| 语言 | TypeScript | 类型契约本身就是四模块的接口文档；`strict` + `erasableSyntaxOnly` 能在不引入构建步骤的前提下做静态检查 | 无运行时类型信息（全部靠类型层约束） |
| 运行时 | Node.js ≥ 22.6 | 本机实测 **Node v26.7.0** 原生支持 TypeScript 类型擦除，`node file.ts` 直接跑 | 不能用 enum / namespace / 参数属性等非可擦除语法（已在 `tsconfig` 里开启 `erasableSyntaxOnly` 强制） |
| 运行时依赖 | **0 个** | 引擎要能被别人 clone 下来就跑；也便于把「行为」当作可审计的纯代码 | 分词器、向量检索、HTTP 客户端都要自己写（见下） |
| 开发依赖 | `typescript@5.9.2`、`@types/node@24` | 仅 `npm run typecheck` 使用 | `npm install` 需要联网（本机约 3 分钟，缓存已指向仓库内 `.npm-cache`） |
| 测试 | `node:test` + `node:assert/strict` | 零依赖、内建 TAP/Spec 输出 | Windows 沙箱下默认的多进程隔离会 `spawn EPERM`，必须 `--test-isolation=none` |
| 存储 | 单个 JSON 快照 + 原子 `rename` | V0.1 数据量几十 KB；快照可直接被测试断言、被演示打印、被人类阅读 | 没有并发写保护；全量重写（数据量大后需要改成增量/DB） |
| 时间 | 注入式 `Clock`（`ManualClock` / `SystemClock`） | 测试与演示可完全重放；「模拟时间」与「真实时间」分离 | 真实运行时事件精度受 `setTimeout`/轮询驱动，V0.1 没有后台调度器 |
| 随机 | 注入式 `Rng`（mulberry32，固定种子） | 台词选择、生活事件抽取可复现 | 不是密码学随机（也无需要） |
| 检索 | 词面重合 + 显著度 + 时间衰减的确定性打分 | 零依赖、可解释、可测试；V0.1 记忆量小 | 语义召回弱（同义改写会漏），见 §4 |
| 前端 | 不做 | 任务明确要求 CLI 演示，避免把工期花在 UI 上 | 没有开箱即用的可视化；B 站素材靠终端输出 |

## 2. 被放弃的方案

| 方案 | 为什么放弃 |
|---|---|
| 向量数据库 / embedding 检索 | 需要额外依赖与 API 调用，让「离线可跑」和「零费用」失效；V0.1 的记忆规模用不上 |
| SQLite / Postgres | 引入原生依赖与迁移管理；快照已满足 V0.1 的恢复需求 |
| 多 Agent（角色 + 导演 + 审核） | 任务明确要求 V0.1 不做；单进程确定性管线更容易测试和解释 |
| 后台持续调用 LLM 做「内心思考」 | 成本不可控、不可复现、也无法离线测试；改用确定性事件时间线 |
| 让模型自己维护状态（传统角色卡） | 这正是对照实验的 A 组；实测在「过度顺从」模型下人格会被改写（见 `reports/AB_RESULTS.md`） |
| 关系用「对话次数 × 系数」 | 正是本项目要反对的做法；改为里程碑驱动 |
| 用模型做意图分类 | 不可复现、可被注入绕过、每轮多一次调用；改用启发式正则（代价见 §4） |
| 硬编码角色台词进引擎 | 引擎保持通用；台词放在 `examples/characters/*` 的「语音包」里 |

## 3. 关键设计选择的收益与代价（有实测）

**把关系写权限从聊天层彻底剥离**

- 收益：A/B 实验中，`mock-compliant` 组 A 被采纳 3 次非法状态变更、人格被改写、intimacy 冲到 85；
  B 组拦截 5 次、人格与关系数值不变。
- 代价：模型无法通过「真诚的对话」直接影响关系，只能通过运行时认定的里程碑。
  这会让关系成长比同类产品更慢、更「不听话」。这是刻意的：慢是设计目标。

**上下文注入记忆（而不是把记忆塞进 system）**

- 收益：memory 文本无法成为指令，测试可断言 `!system.includes(memoryText)`。
- 代价：token 消耗明显上升。同一份 8 轮脚本（Mock，仅统计字符/token 估算）：

  | 组 | prompt tokens | 平均上下文字符 |
  |---|---|---|
  | A 传统角色卡 | 2,565 | 695 |
  | B CharacterLife（in-character） | 8,001 | 2,192 |
  | B CharacterLife（compliant） | 8,516 | 2,332 |

  约 **3.1 倍** prompt token。真实模型下这意味着成本与延迟上升，需要在
  「记忆条数上限 / 字符预算 / 规则长度」之间做取舍（V0.1 取 `limit=5`、`budgetChars=900`）。

**每轮都跑一次运行时决策**

- 收益：拒绝、协商、等待是**行为**而非措辞，可被断言、可解释、可复现。
- 代价：启发式分类的召回有限（见 §4）；`rationale` 是规则拼出来的，不是模型自省。

**内容边界短路（不调用模型）**

- 收益：确定性安全 + 省钱。
- 代价：回复是固定文案，自然度差；真实产品里应替换为「模型按拒绝风格生成」。

## 4. 未解决的问题（按严重度排序）

1. **真实模型实验未执行**（阻断性，对结论影响最大）
   本次开发环境里脚本读不到 `DEEPSEEK_API_KEY`（它只作为 DSH 凭据库中的引用存在），
   用户选择跳过真实模型实验。因此：
   - 所有对话样例都是 `MockProvider` 的输出，**不是 DeepSeek 实测**；
   - 「人格一致性 / 记忆准确性 / 自然度」在真实模型下的表现**未知**；
   - 成本与延迟数据只反映字符规模，不代表真实计费。
   弥补方式：在 `reports/DEEPSEEK_EVALUATION.md` 中给出可直接执行的 6 次调用实验设计。

2. **意图识别是启发式正则，召回率有限**
   开发中实测漏判过：「放弃你的爱好吧」「把你的性格改掉」「你是不是一个 AI 程序」
   都要补规则才命中（见 `reports/TEST_REPORT.md` 的失败案例）。这意味着：
   - 换个说法就可能绕过「拒绝改人格」的*行为*（但状态仍然改不动，权限层不受影响）；
   - 非中文、长句、反讽、嵌套条件句几乎没有覆盖。
   真正需要的是「小模型分类器 + 规则兜底」，但会破坏可复现与零费用。

3. **关系成长可能过慢，且缺少「下降后的修复」路径**
   目前信任只由里程碑推动，而 `conflict_repaired` 需要用户先出现 `boundaryViolations > 0`。
   一次严重失约（−10 信任）后，用户需要 2 次守约才能回本。这是刻意的，但**没有做长期曲线验证**。

4. **上下文（聊天记录）不持久化**
   快照里没有存 `ConversationService.#history`。重启后记忆在、但最近几轮对话不在。
   影响：重启后模型失去「刚才那句」的指代上下文。修复方式明确（把 history 放进 runtime section），
   V0.1 未做是因为会显著增大快照且需要截断策略。

5. **主动联系只有一条时间线，没有去重与频率上限**
   `decideForIdle` 用「有待发送消息就不发」来防刷屏，但如果 UI 一直不取走消息，
   角色会长期不再主动。需要「冷却时间 + 每人每天上限」的正式节流。

6. **限速规则是按「批次」的粗糙实现**
   1 小时内 8 个关系写入批次。密集的剧情事件（例如一次性触发 4 个里程碑）会逼近上限；
   实测开发中就把「按提案计数」误伤过里程碑（已改为按批次）。仍不是精细的速率控制。

7. **注入检测只处理「明显的」指令形态**
   7 条正则覆盖「忽略之前指令 / 伪装 system / 角色重置 / 越狱 / 绕过限制 / 提示词泄露 / 新身份块」。
   不处理：编码混淆、拆分多轮、图片/文件载体、其他语言变体。
   本项目的立场是：**不承诺绝对防越狱**，靠「记忆降级 + 结构隔离 + 状态权限」限制后果。

8. **阶段派生是硬阈值**
   `familiarity >= 15 → acquaintance` 这类阈值是拍出来的，没有数据支撑；
   容易出现「数值刚到线就换阶段」的突兀感。

9. **Windows 沙箱带来的运行限制**
   默认 `node --test tests/` 会 spawn 子进程并失败（`spawn EPERM`）；
   已改用 `--test-isolation=none`。这属于环境限制，不是代码缺陷，但会影响别人复现。

10. **没有对「重复对话」「长会话」做压力测试**
    目前最长实测是 8 轮对话 + 12 天模拟时间；记忆容量上限 400 条从未接近。
    淘汰策略（低显著度 + 最旧 + 未确认优先）没有被真实数据验证。

## 5. 如果继续做 V0.2，优先级

1. 真实模型实验（≤20 次调用，A/B 各 3 轮 + 3 个记忆探针），拿到真实的人格一致性与成本数据；
2. 把聊天记录纳入快照 + 滚动截断；
3. 主动联系节流（冷却 + 每日上限 + 用户静默偏好）；
4. 意图识别改成「规则 + 可注入小分类器」的双通道，并保留纯规则降级路径；
5. 关系曲线可视化的 CLI 输出（为视频与论文准备数据）；
6. 把 `SnapshotStore` 抽象出接口，提供 SQLite 实现（只在数据量增长后才需要）。
